# Pending acceptance after local M41–M45 delivery

This is a prepared acceptance plan, not an execution record or authorization.
M41–M45 local code and offline evidence do not qualify a released RTL agent.
The existing FIFO canary, fixed XOR self-test, scripted ALU discussion, mocked
providers and manufactured run receipts do not prove generation of new RTL.

Do not inspect, adopt, reconfigure or stop the agents account's always-on Docker
runner. A future runtime must have explicit ownership and selection. A saved
profile or successful fixture self-test is not evidence of a usable real backend.
Any required runtime/image/SDK downloads or installations need separate approval.

## Freeze and authorization before M46

1. Record the exact locally integrated commit, source/lock/artifact hashes and
   existing local evidence manifests. Preserve all previous runs and failures.
2. Select the exact provider/model, credential-reference name, owned runtime,
   immutable image and resource limits. Credential values must never enter logs,
   artifacts, transcripts or exports. These choices remain unapproved.
3. Approve a concrete bounded run plan with per-scenario and aggregate call/token,
   repair, step and time ceilings, plus a monetary ceiling when actual pricing is
   available. Unknown usage/cost remains unknown; do not substitute zero.
4. Choose the held-out task after the source candidate is frozen. Record its
   requirements before generation without leaking it into developer fixtures.
5. Create isolated qualification projects and retain content-addressed reports.
   No accepted run may silently replay an uncertain operation or reuse stale
   approval/simulation evidence. Resume preserves consumed budgets and warnings.

No live controller is supplied here: exact provider/runtime choices and effect
budgets must first be concrete and explicitly approved. Existing local handoff
controllers are development validation, never customer setup or live authorization.

## Live scenario matrix

| Scenario | Required observations | Acceptance evidence |
| --- | --- | --- |
| Interactive ALU | Requirements clarified by the real lead; user reviews interface, arithmetic/flag/overflow semantics and corners | Newly generated RTL, independent model and DV, fresh run, requirement/test links and independent adequacy review |
| Sequential counter in batch | Reset/enable/wrap behavior and assumptions remain explicit; delegated scope/budgets survive resume | New artifacts and run receipts; recorded warnings and complete bounded accounting |
| Held-out circuit | Task selected after freeze; no solution copied from fixtures or pre-existing canaries | Requirement provenance, independent collateral, fresh execution and reviewed corner coverage |
| Imported unfamiliar RTL | Anchored explanation reviewed against actual sources; feature proposal has exact writable scope | Original hashes preserved, reviewed change, fresh model/DV/simulation and independent review |
| DV-only improvement | RTL and reference model unchanged; tests check meaningful missing behavior | Before/after byte comparison, strengthened checks, fresh passing run and adequacy evidence |
| Failed design and experiment | Diagnose a real observed failure; repair stays in approved scope; compare identical workloads | Retained failed run, diagnosis anchors, changed artifacts, rerun and explicitly bounded comparison claims |

Each accepted scenario must preserve versioned role context digests, reviewed
requirements, artifact hashes, manifest, run intent/runner/toolchain bindings,
results, model checks, waveform, diagnostics and final independent review.
Require evidence that checks can detect the relevant incorrect behavior; passing
tests alone are insufficient. Model/DV generation must remain independent of RTL
text. A label, anchor, requirement link or reviewer assertion is not by itself
semantic proof. No synthesis/PPA, formal equivalence, FPGA or timing claim is in V1.

Add a controlled interruption/recovery check only within the approved effects:
retain the exact intent, stop before blind replay, recover only the owned runtime,
and show that budgets/warnings and portable evidence remain intact. An uncertainty
record is a valid failure outcome; it must not be rewritten as a passing run.

## Release decision

After all acceptance gates pass, review a distinct immutable OpenRTL release
identity and exact file manifest. Re-run packaged clone/install/restore examples
without editable siblings or development handoff scripts. Bind qualification to
the implementation revision and retained evidence, not to a circular self-hash.
Request explicit approval for the exact remote branches/tags/assets/publication.
Only anonymous verification of the published bytes establishes public delivery.
Until then all OpenRTL continuation commits remain local and unpushed.
